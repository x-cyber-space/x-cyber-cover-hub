# X-Cyber-Cover-Hub 技术架构与开发规范

> **组织**：`x-cyber-space`
> **项目名**：`x-cyber-cover-hub`
> **开源协议**：`GNU Affero General Public License v3.0 (AGPL-3.0)`
> **语言与技术栈**：`Go (Golang 1.25+)`，零 CGO，编译为单一静态二进制。

---

## 1. 项目定位

为自建媒体服务器与音乐播放器提供**本地专辑封面聚合与中转**。与姊妹项目 `x-cyber-lrc-hub`（歌词）配对使用，但**刻意独立成库**，原因见第 2 节。

- **按专辑而非按歌曲组织**：一张专辑一份封面，十二首歌共享。
- **字节中转而非 URL 转发**：两个源的图床都做 Referer 校验，直连上游 URL 通常拿不到图。
- **宁 404 不猜错**：封面会被写进音频文件的 ID3/FLAC 标签，错了是永久的。

---

## 2. 为什么和歌词服务分开

这不是偏好，是三条相互独立的理由：

### 2.1 匹配维度不同，共享核心会退化为烂抽象

| | 身份维度 | 权重取向 |
|---|---|---|
| 歌词 | `title` + `artist` + `duration` | 歌名最重（45/30/25） |
| 封面 | `artist` + `album` | **专辑最重**（专辑 60 / 歌手 40） |

专辑下十几首歌共享封面，所以**歌名与时长对封面是无用信号**。把两边的匹配抽成公共库，就必须参数化"用哪些维度、各占多少权重"——为两个消费者提前抽象，结果两边都别扭。因此本项目**复制而非共享**那部分逻辑，让两边各自演化。

### 2.2 缓存与 HTTP 面是两个物种

| | 歌词 | 封面 |
|---|---|---|
| 数据量 | KB 级文本 | **MB 级二进制** |
| 存储 | SQLite TEXT | SQLite BLOB |
| 响应 | LRCLIB JSON | 图片字节 + `ETag` / `Conditional GET` |

### 2.3 协议身份

`x-cyber-lrc-hub` 的对外承诺是「与 LRCLIB **读取侧**对齐」。封面不属于 LRCLIB 协议，混进同一个仓库会让那句承诺变得含糊，也让人不知道该不该依赖它。

> 代价是基础设施需要复制一份（CI / Dockerfile / Makefile / goreleaser 等约 700 行）。这是**一次性**成本，换来的是两边可以自由分叉。

## 3. 架构

```
                    ┌───────────────────────────┐
                    │   音乐播放器 / 自建媒体库    │
                    └─────────────┬─────────────┘
                                  │ GET /api/cover?artist_name=&album_name=&size=
                                  ▼
                 ┌──────────────────────────────────────────┐
                 │            x-cyber-cover-hub             │
                 │          (本地 Go 单二进制服务)            │
                 ├────────────────────┬─────────────────────┤
                 │  HTTP 层            │  本地持久化缓存层     │
                 │  (Router & 图片响应) │  (SQLite BLOB)      │
                 ├────────────────────┴─────────────────────┤
                 │   两级匹配：归一化精确 → 受控放宽            │
                 │   身份 = (artist, album, size)            │
                 ├──────────────────────────────────────────┤
                 │        并发多源调度（带兜底遍历）           │
                 └───────┬──────────────────────┬───────────┘
                         ▼                      ▼
                  [iTunes（主）]          [网易云（备）]
                  无 key / 无防盗链        覆盖中文曲库
                  可任意改分辨率            Referer 校验
```

## 4. 接口规范

### 4.1 `GET /api/cover`

| 参数 | 必需 | 说明 |
|---|---|---|
| `artist_name` | ✅ | 歌手名 |
| `album_name` | ⚠️ | 专辑名。**强烈建议传**；缺失时无法走缓存，且只能退化为"按歌手猜" |
| `track_name` | | 仅在没有 `album_name` 时用于搜索 |
| `size` | | 边长像素，`64`–`3000`，默认取 `-size`（600） |
| `format` | | `json` → 元数据；否则返回图片字节 |

**默认响应**：图片字节，附 `Content-Type`、`ETag`、`Cache-Control`、`X-Cover-Source`、`X-Cover-Artist`、`X-Cover-Album`。

> `X-Cover-Artist` / `X-Cover-Album` 为 percent-encoded。HTTP 头必须是 ASCII，而中英文专辑名不是——要看明文用 `?format=json`。

**`If-None-Match` 匹配 → `304`，空响应体。**

**`?format=json`**：返回 `artistName`、`albumName`、`source`、`contentType`、`size`、`byteSize`、`etag`、`artworkUrl`（上游地址）、`imageUrl`（**指向本服务，客户端该用这个**）。

### 4.2 状态码

| 码 | `name` | 场景 |
|---|---|---|
| `200` | — | 命中 |
| `304` | — | `If-None-Match` 命中 |
| `400` | `BadRequest` | 缺 `artist_name`；或 `album_name` 与 `track_name` 都缺；或 `size` 越界 |
| `404` | `CoverNotFound` | 没有源能确信匹配 |
| `405` | — | 非 GET，空响应体 |
| `503` | `UpstreamUnavailable` | **所有源都失败**（上游故障） |

`404` 与 `503` 必须分开：把上游故障伪装成"没有这张专辑"会让用户以为自己的元数据有问题。

## 5. 匹配与排序（`internal/matching`）

### 5.1 门（`MatchCover`）

封面身份 = **(歌手, 专辑)**。两级，都不命中即淘汰。

**第 1 级 —— 归一化精确**
归一化 = 转小写 + 剥离括号修饰词 + 折叠空白。
`叶惠美` ≡ `叶惠美 (Deluxe Edition)`，`1989` ≡ `1989 (Taylor's Version)`。
版次标记不应导致重复抓取，这是剥离括号的全部意义。

**第 2 级 —— 受控放宽**
- 多歌手集合匹配：`周杰伦` 可匹配 `周杰伦 / 费玉清`（按 ` / ` ` & ` `、` `feat.` 等切分后比集合）
- 专辑名包含关系（较短者至少 2 个字符）
- 专辑 Bigram 相似度 ≥ `AlbumSimilarityFloor`（0.6）

> **注意**：`NormalizeForSearch`（用于相似度）必须先剥离括号再删非字母数字字符。否则 `(Deluxe Edition)` 会变成字母 `deluxeedition` 残留下来，把本来完全相同的专辑压到满分以下——版次标记的含义恰好相反。

### 5.2 排序（`ScoreCover`）

只对**已过门**的候选排序，不能当作接受条件。

- 歌手：完全一致 40 / 集合重叠 32 / 未知 20 / 其余按相似度 × 40
- 专辑：完全一致 60 / 包含 45 / 未知 30 / 其余按相似度 × 60

专辑权重高于歌手：一个歌手有十几张封面，**认错专辑才是要防的失败模式**。

## 6. 多源调度（`internal/provider`）

源按**配置顺序**即优先级：`iTunes` → `网易云`。并列时前者胜。

### 6.1 为什么 iTunes 是主源

| | iTunes | 国内平台 |
|---|---|---|
| 密钥 | 不需要 | 不需要 |
| 防盗链 | **无** | 有（需 Referer） |
| 分辨率 | **URL 里带，可任意改** | 固定尺寸 / query 参数 |
| 中文曲库 | 弱 | 强 |

分辨率那一条特别有用：`.../100x100bb.jpg` 改成 `.../600x600bb.jpg` 就是同一张原图的另一个尺寸，**一次搜索可以服务任意请求尺寸**。国内平台则要重新发起请求。

### 6.2 兜底遍历（`fetchFirst`）

候选按 (匹配级别 → 源优先级 → 分数) 排序后**逐个尝试下载**，直到拿到图。

这不是可有可无的优化：**iTunes 经常匹配到专辑但那张没有 artwork**，而网易云同一条记录有。消费方会把拿到的字节写进音频文件，所以"试下一个"远好于返回空。

> **去重必须把 source 计入键。** 若按 (歌手, 专辑) 去重，iTunes 的条目与网易云的条目会被合并成一条；主源先试且它没图，兜底就永远走不到。这是实测出来的 bug。

### 6.3 错误语义

`searchAll` 只在**所有源都失败**时返回 error（→ 503）。单个源挂掉或返回空是常态，不算错误。

`fetchFirst` 在所有尝试都失败时返回 `(nil, nil)`——匹配上但没有图，属于 miss。

## 7. 缓存（`internal/cache`）

- **键**：`sha256(归一化歌手 \0 归一化专辑 \0 边长)[:16]`
- **表**：`covers(cache_key UNIQUE, artist_name, album_name, source, artwork_url, content_type, size, byte_size, data BLOB, created_at, updated_at)`
- **身份只在 `matching.IdentityKey` 定义一次**，缓存键与去重共用
- **命中复核**：`cache.Matches` 用与冷启动相同的谓词重新校验。躺错位置的记录不会被返回
- **无 `album_name` 的请求不查缓存**：没有专辑就没有身份，所有专辑会撞成一行；但**按解析出的真实身份写入**，供后续请求命中
- **过期**：默认 90 天。读取时即判定，后台每小时（不低于每分钟）清理
- **边长参与键**：两个源都能从一张原图给出任意尺寸，所以 300px 与 1200px 是不同产物，不该共用一行
- **并发**：连接数固定为 1。SQLite 写本就串行，单次查询是本地小表索引查找；启用 `journal_mode=WAL` 与 `synchronous=NORMAL`

> TTL 的 SQL 修饰符必须用**小数秒**（`-0.060 seconds`）。SQLite 的日期修饰符只有 days/hours/minutes/**seconds**/months/years，写成 `milliseconds` 是无效的，会让 `strftime` 返回 NULL，于是比较恒为假、**每一行都被判定过期**。

## 8. 配置项

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `-port` | int | `3400` | 监听端口 |
| `-cache` | string | `./data/covers.db` | 缓存文件路径 |

## 9. 已知边界

- **无 `album_name` 时只能退化为 MatchRelaxed**，且在极端情况下（同歌手、同专辑名不同唱片）无法区分。调用方应始终传专辑名。
- **不做图片解码**：不校验尺寸是否与请求一致，也不转码。上游给什么就存什么、返回什么。因此 `size` 是"请求意图"而非"保证结果"。
- **不做去重压缩**：同一张专辑的 600px 与 1200px 会各存一份。这是有意的（见第 7 节），代价是磁盘。
- **不做负缓存**：未命中不写库。上游临时故障不该被固化成"这张专辑没有封面"。
